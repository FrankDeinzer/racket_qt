## Ziel (ein Thema)

htdp-libs GUI-Stack unter `PLT_QT=1` als Schluss-Lackmustest: **arbeitet DrRacket-auf-Qt
mit echten htdp-Programmen end-to-end?** Und speziell: triggert der externe
`test-engine:test-dock-size`-Contract-Crash noch — oder hat ihn die jetzt vollständige
Widget-Kette (`canvas-panel%`/`group-panel%`/`tab-panel%` + `show()`-Fix) miterledigt?

## Phase 0 — Umgebung messen (nicht annehmen)

1. `racket --version` **messen** (Report-Header). Erwartet: `v9.2 [cs]`.
2. **Sync-CHECK:** Windows auf neuestem Stand inkl. §22-Fix (Submodul + Umbrella-Zeiger).
   Der §22-Fix hat `shim.cpp` angefasst ⇒ **prüfen, ob die Windows-DLL neuer als
   `shim.cpp` ist; sonst neu bauen** (stale-Shim-Falle — direkt nach dem Pull besonders
   relevant). Steht etwas zurück → STOPP, `AskUserQuestion` (Regel 7).
3. **Windows-Build:** Installation-Link ⇒ `raco setup` nach Racket-Änderungen (hier
   voraussichtlich keine, außer bei einem genehmigten Fix), **nicht** `-S`/`raco make`.
4. **Light Mode:** `framework:white-on-black-mode?` = `#f` (nicht `color-scheme`, §16).
5. Re-Smoke → **3/3**.
6. **Kurzer Menü-Sanity-Check** (Hygiene nach dem §22-Pull): Menüs unter `PLT_QT=1` auf
   Windows unverändert korrekt? (Erwartung: ja — §22 Part B ist auf Windows ohnehin
   No-op, aber einmal verifizieren.)

**Self-Gate Checkpoint 0:** alles grün → Phase 1; sonst **STOPP + Bericht**.

## Phase 1 — htdp end-to-end messen (drei repräsentative Facetten)

In echtem DrRacket unter `PLT_QT=1`, gated Debug hinter `PLT_QT_DEBUG` wo hilfreich,
jeweils Nutzer-bestätigt + Screenshot:

1. **`2htdp/image`** — Bild konstruieren + im Interactions-Fenster anzeigen (Image-Snip-
   Rendering über den Cairo→Backing-Pfad). Rendert korrekt?
2. **`2htdp/universe` big-bang** — kleines World-Programm (`on-tick` + `to-draw` +
   `on-key`). **Besonders interessant für die Kern-Wette:** big-bang treibt eine
   interaktive Schleife — läuft die unter „Racket treibt, Pump blockiert nie" sauber
   (Ticks, Redraw, Tastatur), **ohne eigene geschachtelte Schleife**?
3. **test-engine (`check-expect`)** — htdp-Programm mit ein paar `check-expect`-Tests,
   „Run". Beobachten, was mit dem Test-Report-Dock (`test-engine:test-dock-size`)
   passiert: erscheint es korrekt, oder Crash? Das war der historische harte Absturz —
   **mit offenem Tab reproduzieren** (Trigger zuletzt: ein offener Tab auf Linux, zwei
   auf macOS).

Für jede Facette den **Ist-Zustand** festhalten: funktioniert / kosmetischer Defekt /
harter Crash — und **wo genau**.

## Phase 2 — Einordnen (Nativ als Orakel)

Für alles, was crasht oder anomal ist, **gegen ein natives Backend vergleichen** (dasselbe
htdp-Programm **ohne** `PLT_QT`, also cocoa/gtk/win32):

- **Nur unter Qt kaputt, nativ sauber** → gui-lib/Qt-Lücke → in-scope zum **Messen**
  (instrumentierter Diskriminator: welcher Widget/Pfad). Fix erst nach `AskUserQuestion`
  (Regel 7), nur in `wx/qt/`.
- **Auch nativ kaputt** → externer htdp-lib-Bug (z. B. der `test-dock-size`-Contract),
  **nicht unsere Baustelle** → dokumentieren, **nicht fixen** (Nutzer-Entscheidung,
  htdp-lib bleibt außen vor). Festhalten, dass DrRacket-auf-Qt ansonsten trägt.

## Guardrails

- **htdp-lib NICHT fixen** (extern, plattformunabhängig; Nutzer-bestätigt). Der
  `test-dock-size`-Contract gehört htdp-lib, nicht gui-lib.
- **Echter `wx/qt/`-Bug/-Lücke:** erst `AskUserQuestion` (Scope, Regel 7), dann ggf.
  fixen — nur `wx/qt/`.
- **Fix scheint Shared-Code (`wx/common`) zu brauchen → STOPP + fragen.**
- **Kein `exec()`/keine geschachtelte Schleife.**
- **Nicht cross-platform** hier (macOS/Linux = separater Prompt nach Push).
