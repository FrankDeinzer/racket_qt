# Bericht — Menüleiste sichtbar gemacht + Klick-Öffnen als neues Problem (2026-07-08_prompt)

**Datum:** 2026-07-08
**Plattform:** Windows 11 Enterprise, x86-64 (primäre Entwicklungsmaschine)
**Racket:** v8.18 [cs] · **Qt:** 6.11.0 (`C:\Qt\6.11.0\msvc2022_64`)
**Repro:** `examples/menu-frame.rkt` (Messung) + isolierter Menü-Test ohne `editor-canvas%` (visuelle Bestätigung)
**Startrezept:** `PLT_QT=1` (+ `PLT_QT_DEBUG=1` für Diagnose), Qt-`bin` in PATH; Fork ist verlinktes Paket → plain `racket …` (kein `-S`).

**Kurzfassung:** Die Menüleiste ist auf Windows **sichtbar und korrekt horizontal ausgelegt** (nutzerbestätigt). Die
Ursache war **nicht** die im Prompt vermutete deferred-Layout-Mechanik, sondern ein **fallengelassener Menütitel im
gemeinsamen Racket-Code** — die Prompt-These „Ursache oberhalb der Plattform, im gemeinsamen Racket/Qt-Zusammenspiel"
war korrekt, nur der Mechanismus war ein anderer. Beim Sichtbarmachen ist ein **neues, separates Problem** aufgetaucht:
Ein Klick auf einen Top-Level-Titel **öffnet kein Dropdown** (Event-Loop-Familie, wie der Redraw-Bug).

---

## 1. Phase 1 — Messung (instrumentiert, `menu-frame.rkt`)

Debug-Ausgaben hinter `PLT_QT_DEBUG` an drei Punkten (`shim_menubar_create`, Ende `shim_window_set_menubar`, nach
nativem Show in `shim_window_show`), plus `mb->actions().size()` und, als eigentlicher Diskriminator, Text + Rect
jedes Balken-Items.

**Vor dem Fix:**

| Punkt | mb.height | sizeHint.h | visible | actions | central.geom |
|---|---|---|---|---|---|
| (a) create | 480* | 0 | – | 0 | – |
| (b) set_menubar | 480* | 0 | 0 | 0 | (0,0 100×30) |
| (c1) nach `show()` | **0** | 0 | 1 | 1 | (0,0 600×400) |
| (c2) nach `pump(0)` | **0** | 0 | 1 | 1 | (0,0 600×400) |

(*480 = Qts Default-Größe eines noch nicht ausgelegten Widgets, keine echte Balkenhöhe.)

**Diskriminator-Auswertung (gegen die drei im Prompt vordefinierten Branches):**
- `mb.height() == 0` bei (b) **und** (c), **bleibt 0 nach `pump(0)`** → nominell **Branch I** (Layout läuft nie), und
  ein bloßer Pump behebt es **nicht**.
- `actions == 1` bei Show → die „File"-Aktion **ist** angehängt: Verdrahtung/Daten korrekt, keine fehlenden Items.
- Zentrales Widget `(0,0 600×400)` (volle Fläche, y=0) → **nicht Branch II**: Racket setzt die Geometrie des zentralen
  Widgets nie selbst (verifiziert: `shim_widget_set_geometry` wird nur auf Kind-Widgets aufgerufen); QMainWindow gab
  die volle Fläche, **weil** der Balken Höhe 0 meldet. Effekt von Branch I, keine Racket-erzwungene Geometrie.

## 2. Phase 2 — Kandidaten-Leiter komplett fehlgeschlagen → tiefere Ursache

Die im Prompt vorgesehene Layout-/Polish-Leiter wurde **kumulativ** angewandt, `mb->height()` nach jedem Schritt
gemessen:

```
(c1) after show          → height=0 sizeHint=0
(c2) ensurePolished      → height=0 sizeHint=0
(c3) updateGeometry      → height=0 sizeHint=0
(c4) layout()->activate  → height=0 sizeHint=0
(c5) sendPostedEvents(LayoutRequest) → height=0 sizeHint=0
(c6) adjustSize          → height=0 sizeHint=0
(c7) pump(0)             → height=0 sizeHint=0
```

**Kein Schritt bewegt die Höhe.** Auch `sizeHint().height()` bleibt 0. Das widerlegt die deferred-Layout-These: der
Balken meldet null **Inhalts**größe, nicht bloß ein nicht-aktiviertes Eltern-Layout. Der Detail-Dump zeigt warum:

```
(detail) action[0] text='' visible=1 sep=0 hasMenu=1 rect=(0,0 0x0)
```

Das Top-Level-Item hat ein Submenü (`hasMenu=1`), aber **leeren Text** (`text=''`). Ein Menüleisten-Item ohne Text und
ohne Icon bekommt ein **0×0-Action-Rect** → `QMenuBar::calcActionRects` liefert 0 → gesamter Balken kollabiert auf
Höhe 0. Kein Layout-Trigger kann das beheben, weil es nichts auszulegen gibt.

## 3. Root-Cause — fallengelassener Menütitel im gemeinsamen Racket-Code

`menu-bar% append` (`gui-lib/mred/private/wx/qt/menu-bar.rkt:35`) **erhält** den Titel, **wendet ihn aber nie auf den
QMenu an**:

```racket
(define/public (append menu title)
  (send menu set-parent this)
  (shim_menubar_add_menu qt-menubar (send menu get-qt-menu)))   ; title wird ignoriert
```

Der QMenu wird in `menu%` aus `popup-label` erzeugt (für ein Menüleisten-Menü leer — das Label kommt hier als `title`
an, nicht als `popup-label`), sein Titel bleibt also `""`. `QMenuBar::addMenu(QMenu*)` baut den Balken-Item-Text aus dem
Menütitel → leerer Text.

**Zwei unabhängige Belege:**
- Print im Racket-Layer: `menu-bar% append: title="File"` ↔ Shim beim Anhängen: `incoming QMenu title=''` — der Titel
  ist verfügbar, wird aber nicht durchgereicht.
- Throwaway-Probe (Titel im Shim erzwungen): mit Titel steht `action[0] text='File' rect=(0,0 52x32)` und
  `mb.height=33, sizeHint.h=32` **direkt nach `show()`, ohne jeglichen Layout-Trigger**; QMainWindow versetzt das
  zentrale Widget automatisch auf y=33.

Das erklärt den identischen Ausfall auf allen drei Plattformen **besser** als deferred Layout: **jeder** Top-Level-Titel
ist über diesen gemeinsamen Pfad leer — Null-Breite in-window auf Win32/Linux, titellose (abwesende) Submenüs in der
macOS-NSMenu (deckt sich mit „File/Edit fehlen, nur 🍎 racket").

## 4. Der Fix (nur Titel-Durchreichung, **kein** Layout-Eingriff)

Gespiegelt am bereits existierenden Submenü-Pfad (`shim_menu_add_submenu` → `sub->setTitle(...)`):

- **`qt-shim/src/shim.cpp`:** neue Funktion `shim_menu_set_title(void* menu, const char* title)` → `QMenu::setTitle`.
- **`gui-lib/.../qt/utils.rkt`:** FFI-Binding + Export.
- **`gui-lib/.../qt/menu-bar.rkt`:** `append` ruft `shim_menu_set_title` vor `shim_menubar_add_menu`.

**Nach dem Fix (`menu-frame.rkt`):** `(c) mb.height=33 sizeHint.h=32 actions=1 central.geom=(0,33 600×367)`,
`action[0] text='File' rect=(0,0 52×32)`.

**Visuelle Bestätigung** (isolierter Test `frame% + menu-bar%` mit File/Edit/Help, **ohne** `editor-canvas%`, um den
Redraw-Bug zu umgehen): Balken sichtbar, drei Titel **horizontal** ausgelegt an korrekten x-Positionen
(File @0, Edit @52, Help @107). **Nutzer bestätigt:** „Ich sehe eine korrekte Menüleiste; Hover über einen Titel
hebt ihn hervor."

## 5. Neues Problem — Klick öffnet kein Dropdown (geflaggt, nicht gefixt)

Erst durch den sichtbaren Balken aufgedeckt. **Nutzer:** Hover hebt Titel hervor (Balken lebt, empfängt Maus-Events),
aber ein **Klick öffnet kein Dropdown**.

Diagnose-Probe in `shim_pump` (hinter `PLT_QT_DEBUG`): protokolliert Übergänge von `QApplication::activePopupWidget()`.
Nutzer klickte File/Edit mehrfach → **kein einziges `popup APPEARED`** im Log. `activePopupWidget()` war nie ≠ null.

**Interpretation (Diskriminator des Advisors):** Das Dropdown-QMenu wird beim Klick **nie gezeigt** (nicht: gezeigt und
sofort geschlossen; nicht: off-screen positioniert). Ein geöffnetes Menü bliebe bis zur Verwerfung offen, würde also
vom 50-ms-Poll sicher erfasst — ein Sub-50-ms-Öffnen/Schließen bei jedem Klick ist bei natürlichem Klicken
unplausibel. Es ist **nicht** die in `CLAUDE.md` geflaggte `mapToGlobal`/`client-to-screen`-Positionierungslücke (es
entsteht kein Popup, das man fehlplatzieren könnte).

**Einordnung:** Event-Loop-Familie — dieselbe Wurzel wie der (explizit out-of-scope) Redraw-Bug. Ein echter Fix würde
das `pump(0)`-statt-`exec()`-Event-Loop-Modell berühren, was die Session-Guardrails ausdrücklich verbieten
(kein `exec()`, keine geschachtelte/„bis idle"-Schleife, „NUR die Menüleiste").

## 6. Was widerlegt/ausgeschlossen wurde

- **Deferred-Layout-These (Leithypothese):** widerlegt. Mit korrektem Titel ist die Höhe direkt nach `show()` korrekt,
  ohne jeden Layout-Trigger; ohne Titel behebt **keiner** der Trigger etwas. `show()` legt auf Windows synchron aus,
  sobald Inhalt existiert.
- **Branch II (Racket-Geometrie überdeckt Balken):** ausgeschlossen. Racket setzt die Geometrie des zentralen Widgets
  nie; QMainWindow reserviert den Streifen selbst, sobald der Balken echte Höhe meldet.
- **`setNativeMenuBar`:** war nie relevant (bereits im Prompt verworfen; `isNativeMenuBar()==0` auf Windows bestätigt).

## 7. Konsequenz für Doku

Die im Prompt vorgeschriebene HACKING.md-Lektion („QMenuBar bekommt unter pump(0) nie eine Layout-Runde; Fix =
synchroner Layout-Durchlauf; `QMenuBar::height()` ist der Diskriminator") ist **inhaltlich falsch** für diesen Bug und
darf so **nicht** eingetragen werden. Korrekte Lektion:

> **Menüleiste — leerer Menütitel kollabiert den Balken.** `menu-bar% append` bekam den Titel, reichte ihn aber nie an
> den QMenu. `QMenuBar::addMenu(QMenu*)` leitet den Item-Text aus dem Menütitel ab → leerer Titel = 0×0-Action-Rect =
> Balkenhöhe 0 auf allen drei Plattformen (gemeinsamer Racket-Pfad, oberhalb der Plattform). Fix = Titel via
> `shim_menu_set_title` durchreichen; **kein** Layout-Trigger, **kein** `setNativeMenuBar`, **keine** Geometrie-Reservierung
> nötig. Diskriminator ist die Action-**Text**-Länge (0×0-Rect), **nicht** `QMenuBar::height()`.

(HACKING.md/CLAUDE.md-Checkpoint-Tabelle wurden in dieser Session bewusst noch **nicht** geändert — E-0-Menü ist wegen
des offenen Klick-Problems + ausstehender Phase 4 noch nicht sauber grün. Nach externer Abstimmung nachziehen.)

## 9. Vorgeschlagene nächste Schritte (zur externen Diskussion)

1. **Push + Phase 4 (empfohlen, unabhängig vom Klick-Problem).** Der Sichtbarkeits-Fix ist geteilter Racket-Code und
   gilt cross-Plattform. Windows-Push, dann macOS/Linux: Shim neu bauen, mit `PLT_QT_DEBUG` starten, dieselben Zahlen
   holen. Erwartung: Linux zeigt jetzt Balkenhöhe > 0; macOS-globale Leiste zeigt jetzt File/Edit (Titel nicht mehr
   leer). Falls Linux **mit** korrektem Titel weiterhin Höhe 0 zeigt, wäre **dort** doch ein Layout-Trigger nötig —
   erst dann (messgestützt) ergänzen, nicht spekulativ.
2. **Phase 3 (DrRacket-Gegencheck, Windows).** Prüfen, ob der volle Widget-Baum jetzt einen horizontalen File/Edit/View-
   Balken zeigt (statt gestapelt auf gleicher x-Origin). Verbindet den Minimal-Fix mit dem echten Ziel. Rest-Item-
   Layout-Probleme ggf. flaggen, nicht ausfeilen.
3. **Klick-Öffnen — eigene Session, Event-Loop-Thema.** Charakterisiert als „Popup wird nie erzeugt". Optionen, die die
   Guardrails **wahren** könnten (zu prüfen, nicht vorentschieden): (a) Verhält sich das Popup anders, wenn der Pump
   während der Maus-Interaktion feiner getaktet ist (aktuell 50 ms in `queue.rkt`)? (b) Braucht QMenus interner
   Mouse-Grab/Timer eine kontinuierliche Pump-Bedienung, die der Hintergrund-Pump-Thread nicht liefert? — Falls der
   einzige Fix ein geschachtelter/`exec`-Loop wäre, ist das eine Event-Loop-Modell-Änderung und **außerhalb** von „NUR
   die Menüleiste". Vermutlich gemeinsam mit dem Redraw-Bug (gleiche Familie) anzugehen.
4. **Redraw-Bug** (unverändert, separate Session): nur zuletzt getippte Zeile rendert, kein persistenter Backing-Store
   des Editor-Bereichs. Blockiert saubere Screenshots von Fenstern mit `editor-canvas%` (daher hier isolierter Test
   ohne Canvas).
