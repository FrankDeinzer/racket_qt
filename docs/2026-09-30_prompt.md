## Phase 1 — Die zwei P0-Bugs: erst verifizieren, dann fixen

Beide sind statisch lokalisiert und vom Nutzer auf Windows bestätigt. **Trotzdem zuerst
messen** — die statische Analyse sagt, *wo*; die Messung sagt, *was Qt wirklich liefert*.

### 1.1 Bug A — Ctrl+Buchstabe wird verworfen

**Befund (statisch):** Bei gedrückter Ctrl-Taste liefert `QKeyEvent::text()` unter X11 und
Windows ein Steuerzeichen (Ctrl+A → `\x01`) oder einen Leerstring. `key-map.rkt`
akzeptiert als druckbar nur `text-char >= 32`; Buchstaben stehen nicht in der
Sondertasten-Tabelle (`Qt::Key_A` = `0x41`) → `#f`. `canvas.rkt:158` macht
`(when kc …)` → **das Event wird kommentarlos verworfen.** F5 geht (Sondertabelle), reine
Zeichen gehen (≥ 32). Genau das Muster aus drei Windows-Sessions: Ctrl+R tot, F5 geht —
beides Run-Shortcuts, Run immer aktiv, also kann der Enable-Zustand den Unterschied nicht
erklären.

**Vom Nutzer bestätigt (2026-09-30, echte Tastatur, Windows):** Ctrl+A tut nichts.

**Messen vor dem Fix:**
- Im Shim-`keyPressEvent` (hinter `PLT_QT_DEBUG`) je Taste loggen: `key()`, alle
  Codepoints von `text()`, `modifiers()`, `nativeVirtualKey()`, `nativeScanCode()`.
- Per `xdotool key` messen: Ctrl+A…Z, Ctrl+Shift+Buchstabe, Ctrl+Ziffer,
  Ctrl+Satzzeichen (`[ ] ; / , .` — DrRacket belegt einige davon), Alt+Buchstabe,
  Ctrl+Alt+Buchstabe, F-Tasten, Pfeile mit Modifiern, reine Zeichen.
- **Nativ-Spiegel:** dieselben Tasten an ein natives gtk-DrRacket bzw. eine native Probe,
  die die ankommenden `key-event%`-Felder loggt (`get-key-code`, die Modifier und die
  `get-other-*-key-code`-Felder). Das ist der Sollwert, nicht die Doku.

**Fix-Richtung:** Wenn `text()` < 32 oder leer ist und `key()` im druckbaren ASCII-Bereich
liegt, den Key-Code aus `key()` ableiten (Buchstaben klein, außer der native Sollwert zeigt
etwas anderes). Referenzen: `win32/key.rkt` (`override-mapping?`), gtk (keyval). Prüfen, ob
das Qt-Backend die `other-*-key-code`-Felder setzt, die Rackets Keymaps für
Shift-Kombinationen nutzen — wenn gtk/win32 sie setzen und Qt nicht, gehört das dazu.

**Drei Regressions- bzw. Fallenpunkte — ausdrücklich prüfen:**

1. **macOS-Cmd darf nicht brechen.** Cmd-Shortcuts funktionieren seit §58.1 (dort liefert
   `text()` den Buchstaben). Der neue Zweig darf diesen Pfad nicht verändern.
2. **AltGr auf deutscher Tastatur.** Unter Windows ist AltGr = Ctrl+Alt; AltGr+Q muss `@`
   bleiben und darf kein Ctrl+Alt+q-Shortcut werden. `win32/key.rkt` hat dafür eigene
   Logik (`any-control+alt-is-altgr`). Unter X11 kommt AltGr anders (ISO_Level3_Shift).
   **Falls für die Messung das Tastaturlayout umgestellt werden muss: den Nutzer fragen
   (Regel 9).**
3. **Release-Events** (`'release` + `set-key-release-code`, §11) müssen für die neuen
   Codes genauso stimmen.

**Deterministischer Test (neu, Pflicht):** `tests/key-map.rkt` — eine Tabelle von
`(Qt::Key, text-char, mods)`-Tripeln **mit den gemessenen Werten** (nicht angenommenen),
jeweils mit dem erwarteten Racket-Key-Code aus dem Nativ-Spiegel. Enthält die
Linux-Messungen, dazu macOS-Cmd-Fälle und Windows-AltGr-Fälle als Regressionsschutz (hier
nicht messbar — aus Qt-Doku und den Windows/macOS-Reports ableiten und im Test als
„abgeleitet, auf Zielplattform nachzumessen" markieren). Läuft ohne GUI. Das schließt eine
Lücke des Stub-Audits: Das Audit sieht leere Methoden, aber keine Mapping-Lücken.

### 1.2 Bug B — Menü-Öffnen wird als Fokusverlust gemeldet

**Befund (statisch):** `shim.cpp:289` — `focusOutEvent` reicht **jedes** FocusOut
ungefiltert als `on-kill-focus` weiter; `reason()` wird nirgends geprüft. Auf
Windows/Linux sind Menüleisten-Dropdowns `QMenu`-Popups; beim Öffnen schickt Qt dem
fokussierten Widget ein FocusOut mit `Qt::PopupFocusReason`.

**Vom Nutzer beobachtet (2026-09-30, Windows), genau passend:** Edit-Menü öffnen →
Einträge zunächst wählbar → nach weniger als einer Sekunde, **bei offenem Menü**, werden
„Select All" und Co. ausgegraut. Das ist der asynchrone Enable-Recompute aus §37 (Regel 2),
der beim Framework nach dem Edit-Ziel fragt und keines mehr findet.

**Historischer Zusammenhang:** Die Linux-Session vom 16.09. (§36) sah bereits „Copy/Cut
durchgehend ausgegraut trotz Selektion" — das galt mit §37 als erledigt. §37 hat aber den
*Update-Mechanismus* repariert, nicht den *berechneten Wert*. §37 muss nach diesem Fix
**gezielt an Einträgen validiert werden, die vom Edit-Ziel abhängen** (Copy/Cut/Paste/
Select All/Undo).

**Messen vor dem Fix:** `reason()` bei FocusIn/Out loggen, während das Edit-Menü, ein
Kontextmenü und ein `choice%`-Popup geöffnet und geschlossen werden. Nativ-Spiegel: Meldet
gtk beim Öffnen eines Menüs einen Fokusverlust an Racket? (Erwartung: nein.)

**Fix-Richtung:** `PopupFocusReason` in `focusOutEvent` **und** im zugehörigen
`focusInEvent` nicht weiterreichen (sonst unbalanciert). Für andere Gründe
(`ActiveWindowFocusReason`, `TabFocusReason` …) **nicht raten**, sondern das native
Verhalten spiegeln — messen. ABI-neutral, braucht aber Rebuild, um zu greifen.

**Wahrscheinlich mitbetroffen, mitprüfen:** Kontextmenüs (§59), `choice%`-Popups,
Combo-Dropdowns — überall, wo sich ein Popup öffnet.

### Akzeptanztest Phase 1 (echtes DrRacket, `xdotool`, `PLT_QT=1`)

- Text markieren → Edit-Menü öffnen → **Select All / Copy / Cut bleiben mindestens 3 s
  lang wählbar** (der Recompute landet innerhalb ~1 s, also länger beobachten).
- Ctrl+A markiert alles, Ctrl+C/Ctrl+V kopiert und fügt ein, Ctrl+Z macht rückgängig,
  Ctrl+S speichert (auf einer Scratch-Kopie!), Ctrl+R startet Run.
- Kontextmenü im Editor: Copy wählbar bei Selektion.
- **Nativ-Gegenprobe** derselben `xdotool`-Sequenz gegen gtk-DrRacket.

Qt-Button oder eine Liste den Fokus, erreicht vermutlich kein Tastendruck Racket — damit

Escape = Abbrechen in Dialogen betroffen. Messen in einem Dialog mit Button, Textfeld und
Liste, gegen natives gtk. Das ist der Kern von „Tastaturbedienung in Dialogen" und hängt
eng mit 2.1 zusammen.

**2.3 `drag-accept-files`** — jedes DrRacket-Fenster ruft `accept-drop-files #t` auf; eine
Datei aufs Fenster ziehen tut unter Qt nichts. Neuer Shim-Export (`setAcceptDrops` +
Drop-Callback → `queue-event`, Regel 2). **ABI-Änderung → Build-Banner.** Die echte
Datei-aus-dem-Dateimanager-Geste ist per Automatisierung schwer; wenn nicht verlässlich
automatisierbar, als Prüfpunkt in den freien Test (Phase 4) legen, statt einen Test zu
erfinden.

**2.4 `enforce-size`** — dem Fenstermanager echte Min/Max-Größe mitteilen
(`setMinimumSize`/`setMaximumSize`). Neuer Shim-Export → Build-Banner. Test: `xdotool
windowsize` unter das Minimum.

**2.5 Popup-Submenüs** (§59.1-Blindfleck): `append` ruft nie `set-parent` auf ein Submenü
innerhalb eines Popup-Menüs. Klein, gleiche Maschinerie wie §59.

**2.6 `combo-field%`-Dropdown** (Multi-File-Search, `get-file '(common)`). Laut §61 von der
Größenordnung wie §60.6. **Größen-Gate:** zuerst Umfang messen. Passt es in den Block,
bauen (§59-Popup-Infrastruktur wiederverwenden); sonst `AskUserQuestion` mit Aufwandsschätzung.
