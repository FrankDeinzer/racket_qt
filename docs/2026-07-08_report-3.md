## 2. Qt-Skills konsultiert

Vor dem Schreiben von Shim-Code (wie vom Prompt gefordert) via `qt_documentation_search`/`_read`:

- **`QWidget::addAction(QAction*)`**: *"The ownership of action is not transferred to this
  QWidget."* Ebenso `QMenu::addMenu(QMenu*)`: *"This menu does not take ownership of menu."* →
  Konsequenz: eine parentlose `new QAction(label)` bliebe nach `addAction()` ein für immer
  freistehendes Objekt — kein Absturz, aber ein Leak, da `shim_menu_remove_action`→`removeAction()`
  laut Doku nur entfernt, nie löscht. Fix: Action per Konstruktor-Parent (`new QAction(label,
  menu)`) an ihr Menü binden — Standard-Qt-Ownership-Idiom, kein Doppel-Free-Risiko, da nirgends
  im Code ein expliziter `delete` auf eine `QAction*` existiert.
- **`QWidget::mapToGlobal(QPoint)`**: *"Translates the widget coordinate pos to global screen
  coordinates."* Kein gesonderter `mapToScreen`; für Multi-Monitor ist `mapToGlobal` die korrekte,
  DPI-unabhängige Wahl, wenn (wie hier) `QT_SCALE_FACTOR=1` gepinnt ist — kein Skalierungs-
  Sonderfall.

## 3. Phase 1 — addAction-Fix

**1a. Reconciliation:** `shim_menu_append_action` (aus `2026-06-30_report.md`s 15-Funktionen-Liste)
existiert **nicht** im Code (`grep` über gesamtes Repo: nur in Doku-Dateien erwähnt) — kein toter
Pfad zu reaktivieren, echter Neubau nötig, gespiegelt am funktionierenden Submenü-Pfad.

**1b. Fix** (`qt-shim/src/shim.cpp`):

```cpp
void* shim_action_create(void* menu, const char* label, int checkable,
                         shim_callback_t cb, void* ud)
{
    QMenu* m = static_cast<QMenu*>(menu);
    auto* a = new QAction(QString::fromUtf8(label), m);   // Ownership: geparentet an m
    a->setCheckable(checkable != 0);
    if (cb) QObject::connect(a, &QAction::triggered, [cb, ud](bool) { cb(ud); });
    m->addAction(a);                                       // tatsächlich sichtbar machen
    return a;
}
```

FFI-Signatur (`utils.rkt`) und Call-Site (`menu.rkt`s `append`) entsprechend angepasst
(`shim_action_create qt-menu label checkable? cb #f`).

## 5. Phase 2 — mapToGlobal-Fix

**2a/2b.** Neue Shim-Funktion:

```cpp
void shim_widget_client_to_screen(void* widget, int x, int y, int* out_x, int* out_y)
{
    QPoint g = static_cast<QWidget*>(widget)->mapToGlobal(QPoint(x, y));
    *out_x = g.x(); *out_y = g.y();
}
```

FFI-Binding nutzt das `_ptr o`-Out-Parameter-Idiom von `ffi/unsafe`:

```racket
(define shim_widget_client_to_screen
  (get-ffi-obj "shim_widget_client_to_screen" shim-lib
               (_fun _pointer _int _int
                     (out-x : (_ptr o _int)) (out-y : (_ptr o _int))
                     -> _void -> (values out-x out-y))))
```

`window.rkt`s `client-to-screen` ruft das auf `handle` auf (No-op bleibt nur bei `handle = #f`,
z. B. `menu%`/`menu-bar%`, die diese Methode nie aufrufen). `window.rkt` musste `"utils.rkt"` neu
requiren (fehlte vorher; keine Zirkularität, da `utils.rkt` nichts aus `wx/qt/` requirt).
`screen-to-client` bleibt bewusst No-op — wird nur vom `wx/proxy<%>`-Sibling-Remapping-Pfad in
`wxwindow.rkt` genutzt, von keinem Widget dieses Backends bisher ausgelöst; außerhalb des
Prompt-Scopes (nur `client-to-screen`/mapToGlobal).

**2c. Messung:** Rechtsklick im Definitions-Editor von echtem DrRacket bei Fenster-relativer
Position (400,300) → Kontextmenü erscheint bei ca. (403,304), also **am Klickpunkt**, nicht mehr
am Fensterrand/-ursprung wie vor dem Fix. Screenshot in der Session.

Smoke 3/3 weiterhin grün nach diesem Fix.
