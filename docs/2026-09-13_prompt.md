## Die Triage-Regel (unverändert, hat sich bewährt)

1. **Messen**, bis Root-Cause oder Budget erschöpft. Budget = **max. zwei
   Hypothesen-Zyklen** pro Befund. Instrumentierung hinter `PLT_QT_DEBUG`, nach der
   Analyse **vollständig** zurücknehmen (`git status` beweist es).
2. **Root-Cause gemessen + Fix in `wx/qt/`** → **sofort fixen**, eigener Commit, weiter.
   Nicht fragen.
3. **Root-Cause gemessen + Fix berührt Shared Code** (`wx/common`, `framework`,
   `mred/private`, `shim.cpp`) → Advisor-Subagent für das Architekturbild, dann
   `AskUserQuestion` **mit fertiger Empfehlung** (zwei Optionen + Vorschlag).
4. **Budget erschöpft, keine Root-Cause** → festhalten, was gemessen und was
   **ausgeschlossen** wurde, parken, weiter. **Nie ein spekulativer Fix.**

Regel 4 hat sich in der letzten Runde dreimal bewährt (Toolbar-Timing nicht
reproduziert → Datei-Fehlzuordnung korrigiert; Scrollbar-Versuch → sauberer Revert).
Ein dokumentierter Negativbefund ist ein vollwertiges Ergebnis.

## Kontext-Disziplin

Erster Befund im Hauptagenten end-to-end (Methode etablieren), danach Diagnose je Befund
an Subagenten delegieren. **Rückgabeformat knapp:** Befund · gemessene Root-Cause (oder
Budget erschöpft + Ausgeschlossenes) · Datei(en) · Fix in einem Satz. **Keine Logs,
keine Screenshots im Return.** Beim Hauptagenten bleiben: Befundliste mit Status,

**0.6 Viewport-Test für §23.1 (neu, ~15 Minuten, hohe Hebelwirkung).**

Hintergrund: §23.1 hatte „kein Scroll-/Viewport-Problem" geschlossen, weil ein auf

**Korrekter Test:** die Fenstergröße **vor** dem Start setzen, nicht nachträglich —
DrRackets Fenstergeometrie kommt aus `racket-prefs.rktd`. Also: Prefs sichern + hashen
(Disziplin wie gehabt), Fenstergröße dort auf drei deutlich verschiedene Höhen setzen
(z. B. ~500 / ~900 / ~1400 px), je frischer DrRacket-Start, `htdp-image-count-probe.rkt`
(6 Bilder) laufen lassen, **gerenderte Bilder zählen**. Prefs danach zurückspielen.

- **Zahl skaliert mit der Fensterhöhe** → §23.1 ist ein Viewport-/Scroll-Befund und
  gehört in Cluster 2 (Scroll-Block). Ein Backlog-Punkt fällt weg, der Scroll-Block
  bekommt einen fünften Reproduktionsfall. **Im Report klar so ausweisen.**
- **Zahl bleibt konstant 4, unabhängig von der Höhe** → Viewport ausgeschlossen, §23.1
  bleibt eigener offener Punkt. Auch das ist ein wertvolles Ergebnis.

Stützende Indizien für die Viewport-Hypothese (nicht als bewiesen behandeln, nur als
Grund, den Test zu machen): drei Plattformen zeigen drei verschiedene Zahlen bei drei
verschiedenen Default-Geometrien (Windows 6/6, macOS 5/6, Linux 4/6); und die
Linux-Session vom 2026-09-13 fand unabhängig, dass die Interactions-Auto-Scroll-Ansicht
auf nichts reagiert.

**Kein Fix in 0.6, nur Messung.** Ergebnis entscheidet nur über die Einordnung.

## Phase 1 — Vertrags-Audit (Inventar, vor jedem Fix)

Der §26-Fund entstand als Nebenprodukt einer Nutzerfrage („gibt es noch mehr Stellen mit
falschen Konstanten?") und hat auf Anhieb drei echte Lücken zutage gefördert. Das war
Zufall. **Diese Phase macht es systematisch.**

Jede Datei in `wx/qt/` gegen die drei nativen Backends (`wx/win32/`, `wx/gtk/`,
`wx/cocoa/`) vergleichen. Gesucht werden **drei Muster**:

1. **Hartcodierte Konstante**, wo native Backends einen echten Zustand zurückgeben
   (`(define/override (is-shown?) #t)` ist der Prototyp).
2. **No-op-Override** (`(void)`), wo native Backends echte Arbeit leisten
   (`show-children`, `parent-enable` sind bekannte Fälle).
3. **Fehlender Override**, wo alle drei nativen Backends überschreiben (der §27-
   `maximize`/`iconized?`-Fall war genau das).

**Ergebnis dieser Phase ist eine Tabelle**, nicht ein Fix: Datei · Methode · Qt-Verhalten
· natives Verhalten · **wer im Shared Code das konsumiert** (grep in `mred/private/`,
`wx/common/`, `framework/`) · Einschätzung Vertragslüge vs. harmlos.

Die Spalte „wer konsumiert das" ist die wichtigste — sie trennt „Stub, den niemand
fragt" von „Stub, auf dem Shared Code Entscheidungen baut". Nur letztere sind Cluster 1.

**Self-Gate Checkpoint 1:** Inventar vollständig, Klassifizierung begründet →
`AskUserQuestion` **nur dann**, wenn das Inventar deutlich größer ausfällt als erwartet
(Richtwert: mehr als ~15 Vertragslügen) oder wenn Fixes zwingend Shared Code brauchen.
Sonst direkt Phase 2 — die Klasse ist vorab autorisiert.

## Phase 2 — Die Klasse fixen

**2.1 `is-shown?` (§23.3) — der Kern. Messen vor dem Löschen.**

Die naheliegende Lösung ist, die hartcodierten Overrides in `panel.rkt`, `list-box.rkt`,
`tab-panel.rkt`, `slider.rkt`, `radio-box.rkt`, `group-panel.rkt`, `button.rkt`,
`choice.rkt`, `check-box.rkt`, `message.rkt` einfach zu **entfernen**, damit die
Basisimplementierung aus `wx/qt/window.rkt` greift (so macht es win32).

**Das ist erst richtig, wenn die Basis die Wahrheit sagt.** Zuerst messen: pflegt
`wx/qt/window.rkt`s `shown?`-Feld den realen Zustand — wird es bei `show`/`hide`
tatsächlich gesetzt, und zwar auch für Kinder? Qts `show-children` ist ein dokumentierter
No-op (`window.rkt:167`) — wenn dadurch Kind-Flags nie gesetzt werden, ersetzt das
Entfernen der Overrides nur eine Lüge durch eine andere (`#t` immer → `#f` immer), und
das wäre schlimmer, weil dann Dinge unsichtbar behandelt werden, die sichtbar sind.

Also: erst die Basis verifizieren (instrumentiert, gegen win32 gespiegelt), nötigenfalls
**erst die Basis korrekt machen**, dann die Overrides entfernen. Reihenfolge ist hier
der ganze Punkt.

**2.2 Enable-Kaskade (§26 Fund 2).** `parent-enable` ist unter Qt ein reiner No-op, kein
Widget reicht `enable` an Kinder weiter. Native Backends tun das. Analog zu 2.1: gegen
win32/gtk spiegeln, Basis zuerst.

**2.3 Was das Audit sonst in derselben Klasse findet.** Per Regel 2 fixen.

**Akzeptanztest für diesen Block — unzweideutig:**

> `test-dock-size` muss aufhören zu crashen. 1→2-Tab-Sequenz mit
> `examples/htdp-tests-probe.rkt`, **n=3**, Erwartung **0/3 Crash**.

Das ist ein Bug, der auf drei Plattformen 10/10 reproduziert wurde. Wenn er nach diesem
Block noch auftritt, ist die Root-Cause-Kette unvollständig — dann **kein „gefixt" in den
Report schreiben**, sondern messen, was noch lügt.

**Warnung aus §26.1:** dort wurde `is-enabled-to-root?` bewusst **nicht** zu win32s
unbedingtem `#t` gespiegelt, weil win32 das darf (sein `enable` ruft echt `EnableWindow`,
das OS stoppt Input selbst) und Qt nicht (sein `enable` setzt nur ein Racket-Flag). **Beim
Spiegeln nativer Backends immer prüfen, ob die Voraussetzung des Originals unter Qt
überhaupt gilt.** Diese Falle hat schon einmal fast zugeschlagen.

## Cross-Platform-Modell (neu — bitte genau so handhaben)

Die letzte Runde hat gezeigt: die **Validierung** der drei Windows-Fixes auf Linux und
macOS erbrachte **null** neue Produktbefunde (18 Kategorie-Prüfungen, identische
Ergebnisse, byte-gleiche Zustandstabellen). Was Linux/macOS an Wert lieferten, kam aus
den *freien* Teilen, nicht aus der Validierung.

Deshalb ab jetzt getrennt:

- **Divergenzmessung** (sieht der Bug woanders gleich aus?) → **an den Anfang** eines
  Blocks, aber nur, wenn der Bereich schon einmal Plattformunterschiede gezeigt hat.
  Für Cluster 1 trifft das **nicht** zu: reine Racket-Logik im Fork, identischer Code auf
  allen drei Maschinen, kein nativer Aufruf beteiligt. Deshalb hier keine.
- **Validierung** (funktioniert der Fix woanders auch?) → **gebündelt**, nicht pro Block.
  Diese Session wird gesammelt und später zusammen mit dem Geometrie- und dem
  Scroll-Block in **einem** Durchlauf je Plattform validiert.

**Konkret für diese Session: Linux fixt, committet, pusht — Windows/macOS bleiben
unangetastet.** Im Report festhalten, was später zu validieren ist.
