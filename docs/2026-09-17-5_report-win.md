# Report — Windows: Zombie-Befund mit einer echten langen Live-Sitzung geprüft (2026-09-17, 5)

**Bezug:** Fortsetzung von `docs/2026-09-17-3_report-win.md`, das den Windows-Zombie-Fund
aus `docs/2026-09-17-2_report-win.md` auf n=1 zurückstufte, weil fünf kurze,
gezielte Reproduktionsversuche keine lange, interaktionsreiche Sitzung nachstellen
konnten — genau die Eigenschaft, die den ursprünglichen Fund umgab (er trat als
Nebenbefund am Ende eines langen Test-Sweeps auf). Nutzerauftrag dieser Session: diese
Lücke schließen, eine echte lange Live-Sitzung fahren statt einer kurzen rekonstruierten
Sequenz.

## Wichtige Einschränkung des Testumfangs

Die `2026-09-17-2`-Sitzung, die den Zombie beobachtete, bestand aus zwei unterschiedlichen
Test-Formen: (a) mehreren **separaten, kurzlebigen `racket`-Prozessen** für Teardown-,
Zwischenablage- und Mausrad-Proben, und (b) **einer** länger laufenden echten
DrRacket-Instanz für die Preferences-/Menü-Punkte. Diese Session deckt **nur Form (b)**
ab — eine einzelne, lange, vielseitig genutzte DrRacket-Instanz. Die Mehrprozess-Form (a),
bei der mehrere `racket`-Prozesse zeitlich verschachtelt liefen, wurde **nicht**
nachgestellt. Der Befund bleibt also für diese Form offen, falls er erneut auftritt.

## Durchführung

`tasklist` vor Sessionbeginn geprüft (keine stehengebliebene `DrRacket.exe`/`racket.exe`
— Single-Instance-Falle ausgeschlossen). `racket-prefs.rktd` gesichert/gehasht
(`prefs-backup\racket-prefs.rktd.2026-09-17-5`, SHA256 `6e5f3b21…`).

Eine reale DrRacket-Instanz (`PLT_QT=1`) über ~20 Minuten Sitzungsdauer (laut
Session-Zeitstempeln der begleitenden Werkzeugaufrufe, nicht künstlich verzögert, sondern
durch die tatsächliche Abfolge vieler echter Interaktionen) wie folgt genutzt:

1. Autosave-Recovery-Dialog beim Start abgelehnt (Beleg, dass eine frühere Session hart
   beendet wurde — sagt nichts über den Mechanismus, nur dass *irgendetwas* damals nicht
   sauber herunterfuhr).
2. Text in Tab 1 eingegeben, mehrfach per **echtem Mausklick auf den Run-Toolbar-Button**
   ausgeführt (nicht F5 — Klick ist die zuverlässigere Methode laut
   `docs/2026-09-11_report-win.md`).
3. Zweiten Tab geöffnet (File → New Tab, Mausklick), eigenen Text eingegeben, ebenfalls
   per Run-Klick ausgeführt.
4. Preferences geöffnet (Edit → Preferences, Mausklick), zum Colors-Tab gewechselt, das
   `'(auto-vscroll)`-Panel per UIA `RangeValuePattern.SetValue(Maximum)` gescrollt, „Style
   & Color Names" geklickt (öffnet Unterdialog), Unterdialog per OK geschlossen, Editing-Tab
   kurz angesehen, Preferences per OK geschlossen.
5. Cross-Tab-Zwischenablage: in Tab 1 Edit → Select All → Copy (Mausklicks), zu Tab 2
   gewechselt, Edit → Paste (Mausklick) — Text erfolgreich eingefügt.
6. Tabs-Menü geöffnet (Previous/Next Tab bei zwei Tabs korrekt aktiviert, s. u.),
   Racket-Menü geöffnet/geschlossen, erneuter Run-Klick auf Tab 2.
7. Hauptfenster per echtem Klick auf den nativen Schließen-Button geschlossen.

## Ergebnis

**Zwei separate „Warning — file not saved"-Dialoge** erschienen nacheinander, einer pro
unsaved Tab (Untitled 2, dann Untitled), an identischen Bildschirmkoordinaten — bestätigt:
ein künftiger Repro-Versuch mit mehreren offenen Tabs muss **N Dialoge** behandeln, nicht
einen. Beide per echtem Klick auf „Don't Save" bestätigt.

**Prozess beendete sich sauber** — `Get-Process` unmittelbar danach: kein Eintrag mehr,
`tasklist` bestätigt leer. **Kein Zombie**, trotz zwei Tabs, mehrfacher Codeausführung,
Preferences-Dialog samt Unterdialog und Cross-Tab-Clipboard-Operation in einer einzigen,
über rund 20 Minuten genutzten Instanz.

`racket-prefs.rktd` hatte sich durch die Preferences-Nutzung tatsächlich verändert
(Hash-Mismatch nach der Sitzung) — aus dem Backup zurückgespielt, Hash danach identisch
zum Backup verifiziert. Bestätigt die bestehende Memory-Regel: GUI-Automatisierung ändert
Prefs auch ohne bewusstes Setzen einer Option.

**Insgesamt jetzt 6/6 saubere Prozessenden** über beide Sessions (2026-09-17-3: 5, davon
2 bare Proben + 3 kurze DrRacket-Läufe; 2026-09-17-5: 1 lange Sitzung) — keine reproduziert
das ursprüngliche Symptom.

## Nebenbefunde (beiläufig bestätigt, nicht Ziel dieser Session)

- **`SendKeys("^v")` erreicht den Qt-Editor nicht zuverlässig, Edit-Menü → Paste schon.**
  In zwei unabhängigen Versuchen (dieser Session und der vorigen) fügte `^v` per
  `SendKeys` **keinen** Text ein, obwohl `SetForegroundWindow`/Klick-Fokus vor dem Aufruf
  verifiziert wurden und die Zwischenablage nachweislich den erwarteten Text enthielt
  (`Get-Clipboard`-Äquivalent bestätigt). Derselbe Text über **Edit → Paste per Mausklick**
  fügte sich hingegen korrekt ein (sichtbar an der richtigen Cursorposition). Einfache
  Zeichen-`SendKeys` (Buchstaben, Ziffern, Leerzeichen, `-`) funktionieren dagegen
  zuverlässig — nur Tastenkombinationen mit Modifikatoren scheinen die Qt-Shortcut-Zuordnung
  unter dieser Automatisierungsmethode nicht zu erreichen. Ergänzt die bestehenden
  §21.10/§34.7-Lehren (dort: `ctrl+o`/`ctrl+t` unter `xdotool` auf Linux) um einen
  Windows/SendKeys-spezifischen Fall. **Zusatzlehre aus der vorigen Sitzung bestätigt:**
  unescaped `(`/`+` in einem `SendKeys`-Literal sind Metazeichen (Gruppierung bzw.
  Shift) und zerstören den gesendeten Text kommentarlos — für Code mit Klammern entweder
  escapen (`{(}`/`{)}`/`{+}`) oder auf Klammer-Inhalt verzichten.
- **§37 (Menü-Enable-States) und §36 (Zwischenablage) erneut beiläufig bestätigt:**
  Tabs-Menü „Previous/Next Tab" aktiviert bei zwei offenen Tabs; Edit-Menü Copy/Cut
  ausgegraut ohne Selektion, Paste aktiviert nach Cross-Tab-Copy — deckt sich mit den
  bereits dokumentierten Fixes, keine neue Diagnose nötig.

## Einordnung

**Der Zombie-Befund bleibt „unbestätigt", wird aber nicht als „widerlegt" eingestuft.**
Die Ein-Prozess-Variante (eine lange, vielseitig genutzte DrRacket-Instanz) ist jetzt
durchgetestet und zeigt das Symptom nicht. Die Mehrprozess-Variante aus der
Ursprungssitzung (parallele kurzlebige `racket`-Probenprozesse neben einer laufenden
DrRacket-Instanz) wurde nicht nachgestellt und bleibt der nächste Schritt, falls der
Befund erneut auftritt.
