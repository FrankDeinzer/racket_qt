## 4. W3 — Klick-Bug: vier Diskriminatoren

Neues, gated Probe-Skript `examples/menu-click-probe.rkt` (Modi `direct` / `mixed` / `keyboard` /

- `wx/qt/menu-bar.rkt`: `debug-get-appended-menu` (Hash `title → wx-level menu%`, nur gefüllt wenn

### Diskriminator 1 — direkter `QMenu::popup()`, Klick umgangen

Erster Testlauf mit einem Menü, das nur ein Blatt-Item hat (File→Quit, wie im ursprünglichen
`menu-frame.rkt`-Repro): direkter `(send file-wx-menu popup 100 100 #f #f)` **zeigte keinen
Dropdown** — kein `[PLT_QT_DEBUG] popup APPEARED` im 5-Sekunden-Fenster danach.

Das widerspricht auf den ersten Blick der Erwartung aus dem Prompt („JA → Bug isoliert auf
QMenuBar-Klick-Aktivierung"). Der Grund wurde erst durch Diskriminator 4 klar (siehe unten):
das QMenu war schlicht **leer**.

Zweiter Testlauf mit einem gemischten Menü (Blatt-Item „New" + Submenü „Recent" + Blatt-Item
„Save"): derselbe direkte Aufruf zeigte **`popup APPEARED class=QMenu visible=1
frameGeom=(100,100 107x30)`**, gefolgt von `popup GONE`. Die Höhe (30px = eine Zeile) entspricht
genau **einem** sichtbaren Eintrag — dem Submenü „Recent", nicht den beiden Blatt-Items.

### Diskriminator 2 — `QApplication::activeWindow()`

Direkt nach `frame.show()`: **`activeWindow=NULL`**, sowohl im Blatt-only- als auch im
gemischten Testlauf. Ein CLI-gestarteter Racket-Prozess bekommt auf dieser Maschine keinen
Windows-Fokus (deckt sich mit der im Prompt zitierten `SetForegroundWindow`-Vermutung).

### Diskriminator 3 — Tastatur-Aktivierung (F10 / Alt+F via SendKeys)

`SendKeys` (`{F10}`, dann `%f`) an das Probe-Fenster (nach `AppActivate`) zeigte **keine Wirkung** —
kein `popup APPEARED` im Log. **Konfundiert** mit Diskriminator 2: wenn `activeWindow` bereits
`NULL` ist, könnten `AppActivate`/`SendKeys` das Fenster nie erreicht haben. Das Ergebnis ist daher
**inkonklusiv**, nicht als „Tastatur-Aktivierung funktioniert nicht" zu werten.

Du hast statt des isolierten Probe-Fensters direkt das laufende `PLT_QT=1 DrRacket.exe` angeklickt

> „Die Menüzeile ist da und in den einzelnen Menüs gibt es teilweise Einträge. Es gibt also ein

ursprünglichen Hypothese.

## 5. Root-Cause-Kandidat (verifiziert, NICHT gefixt)

`menu%.append` (`gui-lib/mred/private/wx/qt/menu.rkt`) behandelt Submenüs und Blatt-Items
unterschiedlich:

```racket
(define/public (append id label help-or-sub checkable?)
  (define action
    (if (and help-or-sub (object? help-or-sub))
        ; submenu — help-or-sub is platform menu% (or glue extending it)
        (shim_menu_add_submenu qt-menu label
                               (send help-or-sub get-qt-menu))
        ; leaf item
        (let ([cb (lambda (_ud) ...)])
          (shim_action_create label (if checkable? 1 0) cb #f))))
  (hash-set! item-table id action)
  (order-push! id action))
```

`shim_menu_add_submenu` (`qt-shim/src/shim.cpp`) ruft intern `QMenu::addMenu(sub)` auf — das fügt
die Submenü-Action tatsächlich zum Eltern-`QMenu` hinzu. `shim_action_create` dagegen:

```cpp
void* shim_action_create(const char* label, int checkable,
                         shim_callback_t cb, void* ud)
{
    auto* a = new QAction(QString::fromUtf8(label));
    a->setCheckable(checkable != 0);
    if (cb) {
        QObject::connect(a, &QAction::triggered,
                         [cb, ud](bool) { cb(ud); });
    }
    return a;
}
```

erzeugt nur eine freistehende `QAction` und verdrahtet ihr `triggered`-Signal — sie wird **nie**
per `QMenu::addAction()`/`insertAction()` zum `qt-menu` hinzugefügt. `grep -n addAction
qt-shim/src/shim.cpp` liefert **0 Treffer** im gesamten Shim. Die Action landet zwar in Rackets
`item-table` (für Enable/Check/Callback-Dispatch funktionsfähig), ist für Qt aber unsichtbar.

Das erklärt alle vier Beobachtungen konsistent:
- Blatt-only-Menü (File→Quit) → `QMenu` mit 0 Actions → kein Dropdown, egal ob Klick, Tastatur
  oder direkter `popup()`-Aufruf.
- Menü mit Submenü(s) + Blatt-Item(s) (File→„Open Recent"+„New"+…) → `QMenu` mit nur den
  Submenü-Actions → Dropdown erscheint, zeigt aber nur die Submenüs.
- Rein Submenü-Item selbst (z. B. „Recent" mit „doc1.txt") ist wiederum ein `menu%` mit eigenem
  `append` — dessen Blatt-Items haben dasselbe Problem, sind aber nicht Gegenstand dieser Messung.

**Kein Fix in dieser Session** (Guardrail: „Klick-Bug: MESSEN, NICHT FIXEN"). Der wahrscheinliche
Fix — ein fehlender `qt_menu->addAction(action)` bei der Blatt-Item-Erzeugung — ist eine Vermutung
aus Code-Lektüre plus gezielter Verifikation, kein bestätigter Patch, und berührt möglicherweise
das Event-Loop-Modell nicht im Geringsten (reine Qt-Objektstruktur-Korrektur) — muss aber mit
Cross-Platform-Daten und Review bestätigt werden (Spur 2).

## 6. Was das für die ursprüngliche Hypothese bedeutet

Die in `2026-07-08_report.md` §5 formulierte Einordnung („Event-Loop-Familie, dieselbe Wurzel wie der
Redraw-Bug") ist durch diesen Befund **nicht mehr die naheliegendste Erklärung** für das
Kernsymptom (fehlende Blatt-Items). Die `activeWindow=NULL`-Beobachtung und das kurze
`popup APPEARED`→`popup GONE` ohne Nutzerinteraktion (Diskriminator 1, zweiter Lauf) bleiben aber
reale, unabhängig davon bestehende Nebenbefunde, die in Spur 2 mit betrachtet werden sollten —
möglicherweise ein separates, kleineres Fokus-Thema, nicht zwingend derselbe Bug wie die fehlenden
Blatt-Items.
